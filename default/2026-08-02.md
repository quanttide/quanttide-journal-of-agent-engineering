人给 AI 承担的缰绳作用，就是人的。而这个成本你越轻松，你掌握和驾驭 AI 的能力就越强。

那么所谓的 harness engineering 就是把这种经验给显性化。

比如我在写各个语言的项目时，就让他们尽可能地去遵循各个语言的规范。我觉得这是一个很重要的评审过程。

我们整个的开发流程如下：

1. 先写文档：
文档不一定要是 specification，实际上你打算怎么写就不需要那么严格。虽然可以用 specification 来做，但其实没有必要过于严格。

2. 设置测试：
像文档驱动、测试驱动这些方法比上述流程更严格一点，其实会更有用。

3. 特别注意评审：
评审的时候要特别注意，让他先根据社区的规范来，然后再考虑最后怎么去写。

所以真正重要的东西，不是具体那些 harness，也就是那些 Agent 怎么去写，而是这种 harness 机制到底该怎么从我的经验之中拿出来。

我的这套范式虽然和市场上的有一些相关，但又不完全一样。

我们的流程是：先强调设计文档和设计测试，然后设计模块和设计测试实现，接着进行测试和代码实现，最后在评审中不断地整理和重构。

实际上，我们是一套哈纳斯的测试驱动和文档驱动。

我觉得我的方法论最最重要的一点，就是非常强调直接使用 AI 现有的知识，而不是给它增加结构。通过不断简化自己的习惯方式来适应 AI，从而达到一个人机合作的状态。

对，很多结构其实都是这样子，本质上遵循一套循环，有的循环可能更长一点。比如这样一个开发的循环，它的步骤可能比一轮循环更多。

这个循环里面还有一些子循环，要去调用 code agent 去做。我觉得需要在 PI 的基础上进行封装，这是一个比较重要的工作。

对，我觉得这个想法会让我接近我对 harness engineering 理解的本质，而且它很有可能会起到极大的杠杆作用。

Kimi 给了一个概念叫做 Harness as a Process，确实符合我的实践。

我的这种实践，很需要初级的 harness 作为基础去搭高级的 harness。
